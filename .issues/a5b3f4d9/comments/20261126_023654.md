Test strategy (decided 2026-11-25, supersedes the rot13-only note earlier in this issue):

Default: rot13/47 (SubstitutionCipher, needs_key=False, flat .rot13/.rot47 files).
- Already registered: filename2handler('a.rot13') -> Rot13; issubclass(Rot13, EncryptedFile) is True, so the encrypted code paths are exercised.
- Self-inverse, so round-trips need no fixtures.
- Manual testing stays flat: 'cat note.rot13' shows 'uryyb jbeyq', no unzip, no password prompt, no external exe.
- Existing coverage to extend: TestBaseEncryptedRot13 (testsuite.py:955, skips test_same_input_different_crypted_text) and TestFileSystemNotesWriteClassSaveEncryptedRot13 / ...FunctionSave... (:964, :967). Verified: 8 tests, 0.006s, 3 skipped.

Password paths: PurePyZipAES (.aes.zip).
- Wrong key raises BadPassword (verified), so the dangerous recrypt case - re-encrypting with a bad password - is testable.
- Container is a single flat entry 'encrypted.md' (verified), 184 bytes for a short note; the only pain is that the bytes are binary.
- Needs pyzipper/mzipaes; skip_if_missing_handler() already handles absence.

Explicitly NOT doing: a test-only XOR cipher. Deferred as hash:a3f98a9a with the reasoning (a new handler is not test-only - the registry is built by reflection over dir(), so it would ship in a security tool) and the cheaper fallbacks (CcryptExe .cpt, OpenSslEnc10k).

Known trap for whoever writes these tests: is_encrypted('a.rot13') is True while needs_key is False - see hash:10aa0516. Use handler_class.needs_key in new code, not is_encrypted().
