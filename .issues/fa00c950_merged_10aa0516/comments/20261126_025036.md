Fact-finding (2026-11-25):

What rot13/47 actually are: Rot13 uses a fixed byte translation table (A-Z/a-z rotated 13), Rot47 rotates the printable ASCII range. Both are unkeyed and self-inverse. The class name SubstitutionCipher is a misnomer - a substitution cipher is keyed; these are fixed rotations. README.md:624/:642 compounds it by calling them 'Symmetric Substitution cipher'.

What SubstitutionCipher actually does (__init__.py:381-387): description + needs_key=False + a no-op __init__ that ignores key/password. That is all. It exists so the registry loop (:1248-1260) can pick up keyless handlers, and so needs_key has a named home.

Double duty: it is simultaneously (a) an EncryptedFile subclass, which is what 'encrypted' means to every filter, and (b) needs_key=False, which is what 'needs a password' means to the load path. Those two disagree only for .rot13/.rot47 (verified across all registered extensions). See hash:10aa0516.

Naive-fix hazard (verified by simulation): supported_filetypes_info(unencrypted_only=True) at :1631 skips only EncryptedFile subclasses. Reparent SubstitutionCipher to BaseFile and .rot13/.rot47 land in the unencrypted list, so plaintext_filename_filter('a.rot13') flips to True and ptgrep/fts_index default scope changes (:3118, :3241). Any fix must add a third state or make needs_key the discriminator.

Registry hazard: file_type_handlers is populated by the RawFile/SubstitutionCipher/CompressedFile loop (:1248-1260). Renaming the class without updating that loop, or reparenting without adding the new base there, silently drops .rot13/.rot47 and filename2handler raises UnsupportedFile. all_file_type_handlers (:1236-1246) only excludes RawFile, so it is unaffected either way.
