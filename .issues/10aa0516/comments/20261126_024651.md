Registry model, for whoever fixes this (2026-11-25):

The registry has exactly one capability attribute: BaseFile.needs_key (__init__.py:280), default True, overridden False by RawFile (:336), CompressedFile (:350) and SubstitutionCipher (:383). kdf (:279, None = key is the password bytes) is the only other key-related attribute. There is no 'supports a key' flag distinct from 'requires a key', and no public needs_key(filename) accessor - callers must do filename2handler(path).needs_key.

is_encrypted() / encrypted_filename_filter() is the only public predicate, and it answers 'is this an EncryptedFile subclass', which is a proxy that was never the same question. That is the whole bug: two predicates, one concept.

Consumer audit (verified):
- Correct (needs_key): __init__.py:1948 note_contents_load_filename, ptig.py:1139 do_new, testsuite.py:827.
- Wrong (is_encrypted): ptig.py:1302 do_edit, ptcipher.py:186, ptnewline_check.py:105, pttkview.py:177.
- Comment only: ptgrep.py:435.
- ptrecrypt.py:144 constructs in_handler_class(key=password) unconditionally - no check at all; harmless for rot13 (key ignored) and correct for zip (BadPassword on a wrong key), but it means ptrecrypt never asks 'does this need a key?'.

Registry facts that constrain the fix: .rot13/.rot47 are the only extensions where is_encrypted() and needs_key disagree; .gz/.Z are CompressedFile so they are correctly not-encrypted; VimDecrypt is needs_key=True but is only registered when the vimdecrypt lib is present, so a test must not assume it.
